# Restart startup authority

The installed payload remained current, but the observed GUI and owned bridge were running from an older target/release directory. Run and the Start Menu pointed at the installed application. Runtime records showed both an earlier installed launch and the current legacy launch with startupOwner=false. The previous resolver could return no installation, and launch_role then allowed a release to start independently. The exact reason the installation lookup failed during those historical launches is not established; a current registry probe succeeds.

The regression first demonstrated that a release without installation identity still became Standalone. Release identity now fails closed. A shared resolver reads both Windows registry views and falls back to a complete installation under local application data, requiring both the executable and uninstaller. A separate native launcher contains no UI, bridge, startup registration or recovery loop and only starts the resolved installed application. The package build also produces this launcher for replacing obsolete entry points; future UI changes cannot be embedded in that entry point.

Validation so far: failing regression reproduced, then all 43 Rust tests and type checking passed. The launcher probe resolves the canonical installed executable. Windows package, actual deployment, old-path cold/repeated launch and recovery evidence are recorded separately from an actual Windows reboot. Existing data and unfinished drafts must be checked before process changes; Windows reboot/logoff is excluded.
