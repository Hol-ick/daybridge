# Automatic update delivery

The user requested automatic latest-version maintenance and explicitly authorized operational deployment plus witnessing a subsequent real update, preserving memos/settings and without a Windows reboot. The running installation was c1827a8; b4eaedf had not been installed. This feature also carries that notification-safe recovery change forward.

Added distinct release versions, a signed stable GitHub Release pipeline gated on successful verification, and native background update checks. Downloads are signature verified and pinned to this repository's versioned assets. Applying waits for two minutes of input inactivity, collapsed widget, closed editors/settings, and no active or pending memo. A memo lock and handoff gate cover session-start races.

The installation supervisor backs up and verifies program files, checks data-pointer/memo inventory preservation, waits for the exact parent app to exit, stops only its owned bridge, installs silently and verifies new-version/native/UI/bridge readiness. Installer/startup failure restores program files and quarantines the failed version. It does not replace user data, force-close an active new memo, restore underneath a running installer, or request Windows restart/logoff.

Exploration found Windows PowerShell script execution is restricted. The proposed script supervisor was discarded, without changing or bypassing that execution policy. The final supervisor is the installed native executable's isolated update mode. Local signing material is protected outside the checkout; only the public key is committed and the encrypted Actions signing secret was configured using existing repository permission.

Verification before packaging: 54 Rust tests passed, including updater idle/editor/data guards, invalid signatures, live native process identity and real filesystem program-restore scenarios for partial installation and failed startup. Node regression found an old hard-coded application-version assertion, which was updated to compare with the current package version; the corrected package and release suites passed. Remaining Node suites passed in the full run. Type/frontend build passed. No UI layout was changed by this feature. Packaging, publication, bootstrap and the observed higher-version operational update are recorded separately after they happen.

Operational acceptance caught a cold-start gate defect after the signed 0.2.0 transition installation. The running app found release 0.2.193 and verified its signature, but the initial clipped native widget had never passed through the later JavaScript resize command, leaving a cached expanded flag true. Removed that cached flag. The updater now reads the real Win32 window region; an off-screen native test confirms that the initial 64-pixel clipped region permits updating without any JavaScript resize, while expanded and unknown regions remain blocked. All 55 Rust tests passed after this correction. Added one deferred-state event without note text or activity timestamps. The first transition preserved all memo hashes, the storage pointer, schedule/default settings, and browser local-storage files before app launch.

Release setup also found that the repository default branch still pointed to the initial feature branch, preventing GitHub from discovering the new workflow_run publisher. After explaining its scope and reversible effect, aligned the default branch and local origin/HEAD with the established main delivery policy, preserving all branches and history. The verified main run succeeded, and the first signed release workflow completed successfully. Final operational higher-version acceptance remains separate from these package and release successes.

## Witnessed operational update

Completed the fixed 0.2.0 transition installation from source 5b46758, then observed the application itself discover and download stable 0.2.194, verify its signature, defer while input was active, and hand off after the idle gate cleared. The native transaction finished with phase `completed`. The new canonical process reported version 0.2.194, revision 5b46758 and startup ownership. Its bundled bridge was owned by that process, all three surfaces mounted, the memo shortcut registered, and automatic-update startup readiness was acknowledged. No manual invocation of the update supervisor, simulated inactivity, Windows reboot or logoff was used to produce this acceptance.

Independently extracted the actual downloaded installer and passed all ten package execution checks. The installed executable matches that extracted payload. All three existing memo-store files, the storage pointer, and both schedule/default configuration files retained their hashes. Existing browser user preferences were compared through unchanged LevelDB data tables/manifest and parsed before/after WAL user entries; all four previously recorded user entries retained their values. Browser engine diagnostic logs/timestamps change naturally on restart and were not treated as user-setting loss. The Run entry remains the canonical installation, with exactly one installed app process. Fresh update/startup error events were absent; the existing missing-today-board HTTP 404 events remain a separate condition.

Remote Verify Daybridge 39915092229 and signed Publish Daybridge update 39915160632 completed successfully. The subsequent workflow_run publisher also completed without replacing the immutable release. Stable release v0.2.194 contains the installer, updater signature and latest.json. Superseded v0.2.193 is excluded from the stable channel as a prerelease. Private transaction receipts, installation backups and operational identity were retained outside tracked source; no personal memo text, data path or signing secret is published. Ignored local acceptance receipts are `test-artifacts/auto-update-operational-result.json`, `auto-update-final-payload.json` and `auto-update-storage-result.json`.

This completes automatic-update implementation, operational deployment and a witnessed higher-version update. It does not claim new visual-interaction acceptance, a real Kakao notification test, Windows-login verification or completion of the older broad reliability goal.
