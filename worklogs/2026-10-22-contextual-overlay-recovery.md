# Contextual overlay recovery and configurable delay

The user correctly identified that lengthening a periodic raise cannot protect a notification arriving at the deadline. The native watchdog reasserted HWND_TOPMOST even for a healthy widget, and investigation also found an independent production WebView effect calling show_overlay every fifteen seconds and on visibility changes. The previous ten-second adjustment did not remove that second path.

Removed the WebView effect and made native recovery conditional. A visible, on-screen widget that already has its topmost flag does nothing, including when another topmost notification appears above it. A repair waits for the configured quiet period; input/foreground changes, settings, minimization, or an overlapping visible external window reset or block the wait. The Windows observer considers non-activating windows, ignores cloaked windows, and uses the widget's actual clipped region. Immediately before recovery it rechecks current conditions. Automatic restoration preserves a healthy topmost order, or restores a lost flag behind existing topmost windows, without activation. Explicit user show actions remain separate.

Settings -> screen now provides automatic front recovery and a 1–300-second recovery delay, default ten seconds, saved using the existing Save action. Preferences are validated and atomically saved in native app data before changing the live policy; browser previews use isolated browser storage. Drafts survive tab changes. Disabled settings and delay survive reload; invalid values and failed writes preserve acknowledged preferences. No helper prose was added.
