# Ctrl+D 빠른 메모 구현 계획

**목표:** Daybridge 실행 중 Ctrl+D로 별도 메모창을 열고 즉시 입력하며, 닫기·재실행 뒤에도 내용을 보존한다.

**구조:** 기존 고정 Windows 0.61.3의 RegisterHotKey로 단축키를 등록한다. 단일 숨김 메모창과 전용 자동 저장 파일을 사용하며 일정 브리지·원본 노트에 의존하지 않는다.

**제약:** Tauri/Windows 버전 유지, 기존 사용자 자료 보존, 로그에 메모 내용 미기록, 메모창 닫기는 숨김, 기존 위젯 종료 동작 유지. 운영 로그인·데이터 경로 문제는 별도 미해결 항목이다.

- [x] `src-tauri/src/quick_memo.rs`: 메모 저장·읽기·열기·단축키 상태. 임시 파일과 교체, 저장 실패 시 원본 유지, 1 MiB 제한, 실제 저장 회귀 테스트.
- [x] `src-tauri/src/memo_hotkey.rs`: Ctrl+D 등록/해제, 반복 입력 억제, 실패 상태, 종료 정리. `Cargo.toml`에 기존 Windows 라이브러리 기능만 추가.
- [x] `src-tauri/src/main.rs`, `tauri.conf.json`, `capabilities/default.json`: 단일 메모창, 트레이 진입점, 닫기 분기.
- [x] `src/MemoSurface.jsx`, `src/memo/*`, `src/main.jsx`: 즉시 입력·직렬 자동 저장·오류 재시도·독립 부팅. 빠른 편집 순서와 실패 회복 테스트.
- [ ] 타입 검사, Node/Rust 회귀, 독립 패키지 빌드, 실제 화면·저장·전역 단축키 검증. 실행하지 못한 항목은 구분.
- [ ] 이번 변경만 main 커밋·푸시, 원격 검사 확인, MARU 종료 기록.

## 검증 결과

- `pnpm check`, 자동 저장 단위 테스트 2개, `cargo test --locked` 18개 통과. Rust 검사에서 발견한 폴더 경로를 빈 메모로 오인하는 문제를 수정한 뒤 재검증했다.
- `scripts/memo-smoke.py`: 브라우저 6개 검사 통과. 입력 포커스, 한글·이모지 저장/새로고침 복원, 좁은 화면, 저장 실패/재시도, 읽기 실패 보호, 브리지 요청 없음. 520×500 및 340×320 화면과 오류 화면을 직접 확인했다.
- 최종 수정 포함 독립 Windows release 및 NSIS 빌드 성공. NSIS payload 독립 실행 10개 검사도 모두 true다. 실제 사용자 설치·전역 키 조작·로그인 검증을 의미하지 않는다. installer SHA-256: `4ef7e2f6f0ef166897130d170ce41410bac624abde60736cc52412fb9cb1b81c`.
- 전체 Node 회귀는 169개 중 117 통과/52 실패다. 50개는 기존 fixture의 5초 시작 제한을 넘었고 나머지는 저장 잠금/인계 스트레스 실패다. 관련 서버·저장·fixture 파일은 이번 변경에 포함하지 않았다. 환경 영향과 기존 회귀의 정확한 원인은 미확정이며 전체 검증 통과로 보고하지 않는다.
- Windows Computer Use 창 목록 호출이 재시도·커널 초기화 후에도 시간 초과됐다. 실제 Ctrl+D 전역 호출, 네이티브 포커스, X/Esc 숨김과 재호출은 미검증이다. 브라우저 성공을 네이티브 성공으로 대신하지 않는다.
- 현재 운영 앱·Run·사용자 저장 경로 및 기존 다음 로그인 후보는 변경하지 않았다. 새 버전의 실제 설치/운영 전환은 아직 수행하지 않았다.
- 제품 코드 `ee4ffda`는 main에 커밋·푸시했다. [Actions 36956815230](https://github.com/Hol-ick/daybridge/actions/runs/36956815230)은 failure: Node 169개 중167통과2실패. 새 메모2개는 통과했다. 기존 package-bridge 테스트의 runtime 폴더 rename EPERM과 compiler/bridge 동시 저장 검사의 storage_conflict가 원인이다. 후속 native/package CI 단계는 실행되지 않았다. 기존 라이브러리 HWND 컴파일 충돌과는 다른 실패다.
- 위 두 실패의 소스와 로그를 대조했다. package fixture는 이미 자식 종료를 기다리며, 저장 계층은2초 잠금 대기 제한을 명시한다. 일시적인 Windows 파일 점유 또는 부하만으로 원인을 단정하거나 테스트를 건너뛰지 않았다. 빌드 종료 뒤 로컬 회귀 재확인에서도 같은 fixture 시작 제한 초과가 반복되어 중단했으며 첫 전체 실패 결과를 유지한다.
- 검증 결과만 반영하는 후속 문서 커밋은 `[skip ci]`로 중복 검사를 생략한다. 이는 실패한 제품 검사를 성공으로 바꾸지 않는다. 다음 작업은 기존 CI 실패의 원인 재현/해결, 실제 메모 UI 검증, 그 뒤 운영 전환이다.
